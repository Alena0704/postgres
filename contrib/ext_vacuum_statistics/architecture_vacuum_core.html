How VACUUM Works & How Stats Are Collected

A detailed walkthrough of PostgreSQL's lazy vacuum process: three phases, serial vs. parallel index vacuuming, how PgStat_VacuumRelationCounts is populated, and how the hook delivers data to extensions. Special attention to parallel index stats collection and the double-counting prevention mechanism.

The Three Phases of Lazy Vacuum

Phase I — Heap Scan & Pruning
vacuumlazy.c : lazy_scan_heap() ~line 437

What happens page by page

VACUUM reads every page of the table sequentially (using a ring buffer strategy to avoid evicting the shared buffer cache). For each page:

  • Pruning: Removes dead row versions (tuples deleted or updated by committed transactions). Line pointers are set to LP_DEAD.
  • Freezing: Advances tuple xmin/xmax to prevent transaction ID wraparound. Counter: vacrel->tuples_frozen.
  • Dead TID collection: LP_DEAD items are recorded in vacrel->dead_items (a TidStore). These TIDs will be removed from indexes in Phase II.
  • Visibility map: Pages where all tuples are visible (or frozen) get their VM bits set. Counters: new_all_visible_pages, new_all_frozen_pages.

Phase II — Index Vacuuming (Serial Path)
vacuumlazy.c : lazy_vacuum_all_indexes() ~line 2700, lazy_vacuum_one_index() ~line 3220

Serial mode: one index at a time

When ParallelVacuumIsActive(vacrel) is false, the leader process vacuums each index sequentially in a loop:

for (idx = 0; idx < vacrel->nindexes; idx++) { vacrel->indstats[idx] = lazy_vacuum_one_index(indrel, istat, ...); }

For each index, lazy_vacuum_one_index() does:

  • Snapshots buffer/WAL counters: extvac_stats_start_idx()
  • Calls vac_bulkdel_one_index() — delegates to the index AM's ambulkdelete
  • The index AM scans its pages, removes entries matching dead TIDs, returns IndexBulkDeleteResult with pages_deleted, tuples_removed
  • Computes differential stats: extvac_stats_end_idx()
  • Calls hook: pgstat_report_vacuum_ext(indrel, ...) — reports per-index stats
  • Accumulates: accumulate_idxs_vacuum_statistics() — sums index I/O into vacrel->extVacReportIdx for later subtraction from heap stats
Double-counting prevention: Buffer I/O and WAL counters are process-global (from pgBufferUsage / pgWalUsage). Since index vacuuming happens during the same vacuum operation as heap scanning, the heap stats would include index I/O too. To fix this, accumulate_idxs_vacuum_statistics() sums all index buffer/WAL/timing stats into vacrel->extVacReportIdx, and later accumulate_heap_vacuum_statistics() subtracts them from the heap report.

Почему чистка индексов двухфазная?

Индекс чистится в два прохода — bulk delete и cleanup — потому что это разные виды работы:

  • Bulk delete (ambulkdelete) — удаляет конкретные записи, указывающие на мёртвые строки. Вызывается до того, как heap освободит слоты (Phase III), иначе индекс будет указывать на мусор. Может вызываться несколько раз за один VACUUM, если мёртвых строк больше, чем влезает в TidStore.
  • Cleanup (amvacuumcleanup) — финальная доработка: для btree это удаление полностью пустых страниц (half-dead → deleted), обновление metapage и возврат статистики (num_pages, num_index_tuples). Вызывается один раз в самом конце, после всех циклов heap scan.

Hook вызывается после каждого прохода, поэтому на один индекс приходится минимум 2 отчёта: один от bulk delete, один от cleanup. Расширение накапливает оба в одну и ту же pgstat entry.

Phase II — Parallel Index Vacuuming
src/backend/commands/vacuumparallel.c

When does parallel vacuum kick in?

If the table has multiple indexes and max_parallel_maintenance_workers > 0, PostgreSQL launches worker processes to vacuum indexes in parallel. The leader calls parallel_vacuum_bulkdel_all_indexes() instead of the serial loop.

Key point: Only index vacuuming is parallelized. Heap scanning (Phase I) and heap vacuuming (Phase III) are always single-process.

Critical detail for ext_vacuum_statistics: In parallel vacuum, the hook set_report_vacuum_hook is called inside the worker process, not the leader. This means the extension's pgstat_report_vacuum_extstats() runs in a separate process. The extension must use shared pgstat entries (not backend-local memory) to store stats — which it does via pgstat_get_entry_ref_locked().
Buffer/WAL stats in parallel: Workers don't call accumulate_idxs_vacuum_statistics() (that's leader-only, serial path). Instead, each worker's BufferUsage and WalUsage are stored in dedicated DSM slots. After all workers finish, the leader merges them with InstrAccumParallelQuery(). This means the heap stats subtraction (heap_stats -= idx_stats) does not happen for parallel indexes — the buffer/WAL counters from workers are already separate from the leader's heap scanning counters.
Phase III — Heap Vacuuming (Reaping)
vacuumlazy.c : lazy_vacuum_heap_rel() ~line 2846

Reclaiming dead space in the heap

Now that indexes no longer reference the dead TIDs, VACUUM makes a second pass over the heap pages (using the TidStore as a guide). For each page containing dead TIDs:

  • LP_DEAD line pointers are set to LP_UNUSED (space is reclaimable)
  • Page is marked dirty, WAL record written
  • If the entire page is now empty, it can be truncated from the end of the relation

This phase generates additional buffer I/O and WAL that is part of the heap stats (not index stats).

When and where the hook fires

The hook set_report_vacuum_hook is called from 4 code locations. For each index, the hook fires twice (bulkdelete + cleanup). For the table — once at the very end. So for a table with N indexes: 2×N + 1 hook calls total.

/* Subtract index stats from heap to avoid double-counting */
extVacStats->common.total_blks_read -= vacrel->extVacReportIdx.common.total_blks_read;
extVacStats->common.total_blks_hit -= vacrel->extVacReportIdx.common.total_blks_hit;
extVacStats->common.wal_records -= vacrel->extVacReportIdx.common.wal_records;
extVacStats->common.wal_bytes -= vacrel->extVacReportIdx.common.wal_bytes;
extVacStats->common.total_time -= vacrel->extVacReportIdx.common.total_time;
/* ... and so on for all buffer/WAL/timing fields */
Why this matters: Without this subtraction, if you run SELECT total_blks_read FROM pg_stats_vacuum_tables, you'd see index I/O counted twice — once in each index's row, and again in the table's row. The subtraction ensures clean separation: table stats show only heap work, index stats show only index work.
