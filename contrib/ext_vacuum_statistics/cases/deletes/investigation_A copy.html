A DETECTIVE STORY

One small GUC, 59× more vacuum work on a single index

Investigating maintenance_work_mem the way an Andrey Zubkov / pg_profile user would, using only the per-relation vacuum stats

STEP 1 — overview

Something's off — the same DELETE workload runs for minutes on the broken side, seconds on the fixed side.

STEP 4 — per-index

The smoking gun — one index burns it all.

pgbench_accounts has exactly one index (pgbench_accounts_pkey). Per-index vacuum stats for the same phase:

Same index, same number of dead tuples removed. BROKEN read 588× more blocks from the same B-tree to accomplish the same work — and spent 59× more wall-clock time.
STEP 5 — root cause

Why the same index gets re-read 588× more often.

The pg_stat field that explains everything — idx_passes, the number of times vacuum walked each B-tree from root to leaf:

1 430
BROKEN — index passes
3
FIXED — index passes
Each pass = a full B-tree scan to delete the dead pointers held in vacuum's dead-TID buffer. With a tiny buffer, the same 62 500 dead tuples have to be drained in 1 430 chunks — 1 430 full B-tree scans on the same physical index. A bigger buffer absorbs them all at once: 1 chunk, 1 pass.
STEP 6 — mechanism

The chain in seven words.

maintenance_work_mem = 64 kB
  ↓
dead-TID buffer holds ~11 000 entries  (≈ 64 kB / 6 B per entry)
  ↓
62 500 dead tuples ÷ 11 k = 1 430 chunks
  ↓
each chunk = full B-tree scan + WAL FPI burst
  ↓
587× more index reads, 59× more wall-clock time
  ↓
the workload didn't change — the bookkeeping did.
STEP 7 — fix

One GUC.

ALTER SYSTEM SET maintenance_work_mem = '256MB';
SELECT pg_reload_conf();
Same hardware, same workload, same dead tuples — and now the same cleanup runs in 5.7 s instead of 5.6 min. The point of per-relation vacuum statistics is to make this one-line tuning provable from nothing more than a sample-vs-sample comparison.
