How ext_vacuum_statistics Works

This extension gives you detailed metrics about what PostgreSQL's VACUUM process actually does: how much I/O it generates, how many pages it scans, how many tuples it freezes, and how long it takes. All of this happens transparently — VACUUM works exactly as before, but now you can see inside it.

Module 1: What PostgreSQL Already Collects

PostgreSQL Core Vacuum Counters

Every time PostgreSQL runs VACUUM (manually or via autovacuum), the core engine already computes a rich set of internal counters. Think of it like an odometer in a car — the engine tracks everything, but normally these numbers are not shown to you.

Buffer I/O

  • Pages read from disk
  • Pages found in shared buffers (cache hits)
  • Pages dirtied & written back
  • Time spent on reads & writes

WAL (Write-Ahead Log)

  • Number of WAL records generated
  • Full-page images (FPI) written
  • Total WAL bytes produced

Heap Work (tables)

  • Pages scanned & pages removed
  • Dead tuples deleted
  • Tuples frozen (to prevent wraparound)
  • Visibility map pages marked frozen/visible
  • Index vacuum passes count

Timing & Safety

  • Total vacuum time
  • Cost-based delay time
  • Wraparound failsafe triggers
  • Interrupt events
The problem: PostgreSQL collects all these numbers, but historically there was no way for external code to see them after the vacuum finishes. The numbers were computed internally and then discarded (or only partially logged to server log).

Module 2: What ext_vacuum_statistics Adds

Extension The Hook Mechanism

PostgreSQL has a system of hooks — special "connectors" where extensions can plug in their own code. Think of it like a tee-junction in a pipe: the water (data) flows normally, but you install a side-branch to capture a sample.

Our extension uses the set_report_vacuum_hook. At the exact moment when VACUUM finishes processing a table or index, PostgreSQL calls our function and passes all the counters described above. We don't change VACUUM's behavior at all — we just intercept the report.

Extension Statistics Accumulation

Once the extension receives the counters from VACUUM, it stores them in shared memory — a region of RAM that all PostgreSQL processes can access. The statistics are cumulative: each time VACUUM runs on the same table, the new numbers are added to the existing totals. This way you see the full picture over time, not just the last run.

Statistics are saved at three levels:

  • Per table — detailed breakdown for each individual table
  • Per index — separate counters for each index vacuumed
  • Per database — aggregated totals across all tables in a database

Extension Querying the Statistics

The extension exposes three SQL views — just like regular PostgreSQL system views. You query them with SELECT, join them with other tables, filter, sort — nothing special needed:

  • ext_vacuum_statistics.pg_stats_vacuum_tables — one row per table
  • ext_vacuum_statistics.pg_stats_vacuum_indexes — one row per index
  • ext_vacuum_statistics.pg_stats_vacuum_database — one row per database

DBA Guide: Configuration & Usage

How to install, configure, and use the extension day-to-day. Everything here is done through SQL and postgresql.conf — no C code needed.

Installation

1. Add to shared_preload_libraries in postgresql.conf:

shared_preload_libraries = 'ext_vacuum_statistics'

2. Restart PostgreSQL (required for shared memory allocation).

3. Create the extension in each database:

CREATE EXTENSION ext_vacuum_statistics;

Configuration Parameters (GUC)

All settings live under the vacuum_statistics.* namespace and can be changed with ALTER SYSTEM or in postgresql.conf.

Parameter Default What it does
vacuum_statistics.enabled on Master switch. When off, no statistics are collected at all.
vacuum_statistics.object_types 'all' What to track: 'all' (tables + indexes + database aggregates), 'relations' (only tables & indexes), 'databases' (only database-level aggregates).
vacuum_statistics.track_relations 'all' Filter by relation type: 'all', 'user' (only user tables), 'system' (only catalog/system tables).
vacuum_statistics.collect 'all' Which counter categories to accumulate. Comma-separated list:
buffers wal general timing
Example: 'buffers,timing' — skip WAL and tuple counters.
vacuum_statistics.track_relations_from_list off Whitelist mode for relations. When on, only tables/indexes explicitly added via add_track_relation() are tracked.
vacuum_statistics.track_databases_from_list off Whitelist mode for databases. When on, only databases added via add_track_database() are tracked.

Whitelist Management

Tracking Specific Databases

1. Enable: SET vacuum_statistics.track_databases_from_list = on;
2. Add: SELECT ext_vacuum_statistics.add_track_database(oid) FROM pg_database WHERE datname = 'mydb';
3. Remove: SELECT ext_vacuum_statistics.remove_track_database(...);

Tracking Specific Tables

1. Enable: SET vacuum_statistics.track_relations_from_list = on;
2. Add: SELECT ext_vacuum_statistics.add_track_relation(current_database()::oid, 'mytable'::regclass::oid);
3. View list: SELECT * FROM ext_vacuum_statistics.track_list();

Track list persistence: The whitelist is saved to a file on disk (pg_stat/ext_vacuum_statistics_track.oid), so it survives PostgreSQL restarts. When a tracked table or database is dropped, the extension automatically cleans up the list entry.

Querying Statistics

Tables

SELECT * FROM ext_vacuum_statistics.pg_stats_vacuum_tables;

Pages scanned/removed, tuples deleted/frozen, VM pages, buffer I/O, WAL, timing, index vacuum count, missed dead tuples.

Indexes

SELECT * FROM ext_vacuum_statistics.pg_stats_vacuum_indexes;

Buffer I/O, WAL, timing, tuples deleted, pages deleted.

Databases

SELECT * FROM ext_vacuum_statistics.pg_stats_vacuum_database;

Aggregated: buffer I/O, WAL, timing, failsafe & interrupt counts.

Administrative Operations

Reset Statistics

  • SELECT ext_vacuum_statistics.vacuum_statistics_reset(); — reset everything
  • SELECT ext_vacuum_statistics.extvac_reset_entry(dboid, relid, type); — reset one relation
  • SELECT ext_vacuum_statistics.extvac_reset_db_entry(dboid); — reset one database

Memory Usage

SELECT ext_vacuum_statistics.shared_memory_size();
Returns total shared memory used in bytes (~232 bytes per tracked object).

Module: Initialization (_PG_init)

On shared_preload_libraries load, _PG_init() performs:

  • Registers 6 GUC variables under vacuum_statistics.* prefix with check/assign hooks
  • Registers 2 custom pgstat kinds: PGSTAT_KIND_EXTVAC_RELATION (24) and PGSTAT_KIND_EXTVAC_DB (25)
  • Hooks into set_report_vacuum_hook → pgstat_report_vacuum_extstats()
  • Hooks into shmem_request_hook → requests LWLock tranche
  • Hooks into object_access_hook → removes dropped objects from track lists
  • Reserves GUC prefix: MarkGUCPrefixReserved("vacuum_statistics")

Key Encoding for pgstat

Each pgstat entry is identified by (kind, dboid, objid). For relations, objid encodes both relation OID and type:

relid (bits 63..2) Relation OID, shifted left by 2
type (bits 1..0) 0=TABLE, 1=INDEX

#define EXTVAC_OBJID(relid, type) (((uint64)(relid)) << 2 | ((type) & 3))

Registered pgstat Kinds

Kind 24: PGSTAT_KIND_EXTVAC_RELATION

  • Key: (dboid, EXTVAC_OBJID(relid, type))
  • Stores per-table or per-index counters
  • Full PgStat_VacuumRelationCounts struct

Kind 25: PGSTAT_KIND_EXTVAC_DB

  • Key: (dboid, InvalidOid)
  • Stores aggregated per-database counters
  • Only common counters (no table/index specifics)

Module: Accumulation Functions

extvac_store() — Core Storage Logic

// Per-relation storage
if (store_relation) {
  objid = EXTVAC_OBJID(relid, type);
  entry_ref = pgstat_get_entry_ref_locked(
    PGSTAT_KIND_EXTVAC_RELATION, dboid, objid, false);
  shared = (PgStatShared_ExtVacEntry *) entry_ref->shared_stats;
  pgstat_accumulate_extvac_stats(&shared->stats, params);
  pgstat_unlock_entry(entry_ref);
}

// Per-database aggregation
if (store_db) {
  entry_ref = pgstat_get_entry_ref_locked(
    PGSTAT_KIND_EXTVAC_DB, dboid, InvalidOid, false);
  shared = (PgStatShared_ExtVacEntry *) entry_ref->shared_stats;
  pgstat_accumulate_common_for_db(&shared->stats.common, &params->common);
  pgstat_unlock_entry(entry_ref);
}

ACCUM_IF Macro — Category-Selective Accumulation

#define ACCUM_IF(dst, src, field, cat) \
  do { \
    if (evs_collect_mask & (cat)) \
      (dst)->field += (src)->field; \
  } while(0)

Every counter field is guarded by its category bit. If vacuum_statistics.collect = 'buffers,timing', then WAL and general counters are zeroed out — they still exist in the struct but never get incremented.

Module: Cleanup on DROP

evs_drop_access_hook() — object_access_hook

When a table or database is dropped, PostgreSQL fires the object_access_hook. The extension catches OAT_DROP events and:

  • Removes the OID from evs_track_relations_hash / evs_track_databases_hash
  • Saves the updated track list to disk
  • The pgstat entry itself is cleaned up by the pgstat framework automatically
