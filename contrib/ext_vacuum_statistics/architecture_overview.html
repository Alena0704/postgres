How ext_vacuum_statistics Works

This extension gives you detailed metrics about what PostgreSQL's VACUUM process actually does: how much I/O it generates, how many pages it scans, how many tuples it freezes, and how long it takes. All of this happens transparently — VACUUM works exactly as before, but now you can see inside it.

What PostgreSQL Already Collects Inside VACUUM

PostgreSQL Core Vacuum Counters

Every time PostgreSQL runs VACUUM (manually or via autovacuum), the core engine already computes a rich set of internal counters. Think of it like an odometer in a car — the engine tracks everything, but normally these numbers are not shown to you.

Buffer I/O

How intensely VACUUM uses the disk and memory cache.

  • Pages read from disk — each page is 8 KB of table data
  • Pages found in cache (shared buffers hits) — no disk needed
  • Pages dirtied & written back — changes that VACUUM made
  • Time spent on reads & writes — actual I/O wait time

WAL (Write-Ahead Log)

How much write-ahead log VACUUM generates. This directly affects replication lag and disk usage.

  • WAL records — number of log entries
  • Full-page images (FPI) — full page snapshots written to WAL
  • Total WAL bytes — overall WAL volume produced

Heap Work (tables)

The actual cleanup work VACUUM does on table data.

  • Pages scanned & removed — how much of the table was processed
  • Dead tuples deleted — old row versions cleaned up
  • Tuples frozen — rows protected from transaction ID wraparound
  • Visibility map updates — pages marked as all-visible or all-frozen
  • Index vacuum passes — how many times indexes were cleaned

Timing & Safety

Operational metrics: how long things take and whether safety mechanisms triggered.

  • Total vacuum time — wall-clock duration
  • Cost-based delay time — intentional pauses to limit I/O impact
  • Wraparound failsafe triggers — emergency anti-wraparound activations
  • Interrupt events — times VACUUM was interrupted (e.g., by conflicting locks)
The problem: PostgreSQL computes all these numbers internally during every vacuum, but there was no way for DBAs to access them programmatically after the vacuum finishes. The numbers were computed and then discarded, or only partially logged to the server log in text format that's hard to query or aggregate.

What ext_vacuum_statistics Adds

Extension The Hook Mechanism

PostgreSQL has a system of hooks — special "connectors" where extensions can plug in their own code. Think of it like a tee-junction in a pipe: the water (data) flows normally, but you install a side-branch to capture a sample.

Our extension uses the set_report_vacuum_hook. At the exact moment when VACUUM finishes processing a table or index, PostgreSQL calls our function and hands over all the counters described above. We don't change VACUUM's behavior at all — we just intercept the report. Zero performance overhead on the vacuum itself.

Extension Statistics Accumulation

Once the extension receives the counters from VACUUM, it stores them in shared memory — a region of RAM that all PostgreSQL backend processes can access simultaneously. The statistics are cumulative: each time VACUUM runs on the same table, the new numbers are added to the existing totals. This way you see the full picture over time, not just the last run.

Statistics are saved at three levels of granularity:

  • Per table — the most detailed: every counter for each individual table
  • Per index — separate counters for each index that was vacuumed
  • Per database — aggregated totals across all objects in a database

The extension also saves these statistics to disk automatically, so they survive normal PostgreSQL restarts. You don't lose your history when you restart the server.

Extension Querying the Statistics

The extension provides three SQL views — just like the built-in PostgreSQL system views (e.g. pg_stat_user_tables). You query them with regular SELECT, join them with other tables, filter, sort — nothing special needed:

  • pg_stats_vacuum_tables — one row per table, all vacuum metrics
  • pg_stats_vacuum_indexes — one row per index, index-specific metrics
  • pg_stats_vacuum_database — one row per database, aggregated totals

You can also configure which objects to track, which categories of counters to collect, and reset statistics when needed. All through simple SQL commands and postgresql.conf settings.
