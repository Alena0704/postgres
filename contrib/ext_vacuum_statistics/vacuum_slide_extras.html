Pros & Cons

Honest assessment of the extension approach

Pros
✅
Only 2 lines in core
hook + pgstat_register_kind(). Minimal review burden.
✅
Zero overhead when disabled
enabled=off → hook returns immediately, no locks, no shmem writes.
✅
Full pgstat lifecycle for free
Persistence, cross-DB access, reset, LWLock — all from the framework.
✅
Surgical filtering with 6 GUCs
Track only what you need. Runtime changes, no restart.
✅
prev_hook chaining
Multiple extensions coexist safely. Additive, not exclusive.
✅
pg_stat_statements model
Familiar pattern. Core fills struct, extension owns storage.
✅
Auto-cleanup on DROP
OAT_DROP hook removes stale entries. No memory leaks.
Cons / Limitations
⚠
Requires shared_preload_libraries
Server restart needed to install. Can't add on a running cluster.
⚠
pgstat hash has no size limit
Unlike pg_stat_statements (has .max + eviction), pgstat entries persist until restart. 10K tables × 232 bytes ≈ 2.3 MB — acceptable but unbounded.
⚠
Wall-clock timing includes waits
total_time = real elapsed time (I/O wait + lock wait + OS scheduling). Not pure CPU/vacuum work time.
⚠
Cumulative only — no per-run history
Counters only grow. To see per-vacuum-cycle data, need pg_profile or external snapshotting.
⚠
Crash loses recent stats
pgstat flushes to disk on clean shutdown. Crash = some data lost. Same as built-in stats.
⚠
Core patch still needed
The hook itself (set_report_vacuum_hook) requires a 2-line core patch that must be accepted upstream.

Use Cases

When ext_vacuum_statistics saves the day

Autovacuum Tuning
🔧
Is cost_delay too aggressive?
Compare delay_time vs total_time.
If delay_time > 80% → throttle is strangling vacuum.
WAL Spike Investigation
📈
Why did WAL spike at 3 AM?
Check wal_bytes per table.
Find which vacuum generated 8× normal WAL.
Wraparound Prevention
⚠
Is freezing keeping up?
Track tuples_frozen, vm_new_frozen_pages.
Spot tables falling behind.
Index Bloat Detection
📊
Which indexes cost the most?
Per-index blks_read + pages_deleted.
Find candidates for REINDEX.
